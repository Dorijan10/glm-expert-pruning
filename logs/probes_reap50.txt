        // 4. Move 'current' forward to the next node
        current = next;
    }

### Why an Atomic Increment Kills Scaling

In a multithreaded program, you might think, "It's just an integer `++`, how expensive could it be?" The answer lies in how the CPU actually executes an atomic operation.

Here is what happens under the hood when you use a function like `std::atomic<uint64_t>::fetch_add(1)`:

1. **Cache Line Transfer:** The atomic operation requires exclusive access to the cache line containing the variable. If Thread B is currently writing to it, Thread A must wait for Thread B to finish and for the cache line to be transferred across the CPU cores.
2. **Cache Line Flush:** The core performing the atomic increment must flush its store buffer, ensuring the write is committed to the L1 cache (and visible to other cores).
3. **The Loop:** The thread immediately loops back to step 1 and tries to do it again.

**The Real Killer: Cache Line Eviction**
Because the atomic variable is being constantly written to, it can almost never sit peacefully in a core's L1 cache. The moment Core 0 gets the cache line and increments it, it sends an invalidation message to Core 1. Core 1 then requests the line to do its increment, invalidating Core 0's copy. 

This ping-pongging creates a massive bottleneck. The cores spend all their time stalled, waiting for memory synchronization rather than doing actual work.

To determine whether a kernel is memory-bound or compute-bound using measurements alone, you must rely on the **roofline model**—a theoretical framework that uses observed operational intensity to classify bottlenecks. Here's how to do it:

1. **Measure the kernel's total execution time** (or sample it over time).
2. **Measure the total bytes transferred** between the slow external memory and the fast on-chip cache (DRAM ↔ SRAM/L1).
3. **Measure the total floating-point operations** (FLOPs) executed.
4. **Calculate the kernel's arithmetic intensity:** $I_{kernel} = \frac{\text{FLOPs}}{\text{Bytes}}$.
5. **Measure the machine's balance point:** $I_{max} = \frac{\text{Peak FLOP/s}}{\text{Peak Byte/s}}$.
6. **Compare the kernel's intensity to the machine's balance point.**
   - If $I_{kernel} \ll I_{max}$, the kernel is **memory-bound**.
   - If $I_{kernel} \gg I_{max}$, the kernel is **compute-bound**.
   - If $I_{kernel} \approx I_{max}$, the kernel is **latency-bound** (balanced).
